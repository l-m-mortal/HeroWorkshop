# Окно магазина: заметки (v1 — вкладки, v2/v3 — колонка у правого края, v4 — рецепты+раскладка+тумблер)

## v4: составные предметы (рецепты), раскладка впритык к краю, смещённый тумблер (текущая версия)

Три отдельных правки по прямой задаче, все в `shop_jass.py` (+ `_build_parts`/
`_match_by_norm` в нём же) и `docs/SHOP_UI_NOTES.md`, без изменений
`map_fix.py fix_shop_ui`/`collect_catalog`'s calling convention:

### 1. Составные предметы (рецепты)

Раньше клик по товару-рецепту (например, "Vladmir's Offering") продавал
только сам юнит-обёртку — то есть только рецепт-свиток, без компонентов.
Теперь `collect_catalog` (после сборки всех 14 категорий, `_build_parts`)
строит для **каждого** товара таблицу "частей" (`it['parts']`, список
`(индекс_категории, unit-код, стоимость)`), полностью на стороне Python во
время инъекции — не в рантайме JASS:

* Товар сопоставляется с `data/dota2_reference.json`'s `items{}` по
  `workshop.item_base_name()` + нормализации имени (`workshop.norm`), точным
  или нечётким (префиксным, как в `item_list()`) совпадением.
* Если найденная запись имеет `"components"`, каждый компонент так же по
  имени ищется среди товаров **всех** 14 базовых категорий (не только своей).
  Найденный компонент добавляется как отдельная "часть" — рекурсивно (если
  сам компонент — тоже рецепт с вложенными компонентами, разворачивается
  дальше; защита от циклов — `visited` по ключу dota2-предмета).
* Если компонент нигде в базовых лавках не продаётся, он пропускается, и
  печатается одна строка с указанием причины — "только в секретной/боковой
  лавке" (проверено отдельно по `w.shops()` для `uC74`/`u010`) или "не
  продаётся ни в одной лавке этой карты" (на тестовой карте вариант B
  встречается чаще — это не полный набор предметов Dota 2, а урезанный
  каталог "Hero Workshop"). Пример вывода (полный список — в логе
  `map_fix.py shop-ui`, без `--apply`):
  ```
  skipped component 'Sacred Relic' of 'Divine Rapier' (secret/side shop only)
  skipped component 'Blitz Knuckles' of 'Monkey King Bar' (not sold in any shop on this map)
  ```
  На тестовой карте (`test_shop.w3x`, 160 товаров) **54 товара** получили
  ≥2 части (реальный разворот рецепта), например `Battle Fury` — 7 частей
  (сам рецепт + 6 найденных компонентов), `Aghanim's Scepter` — 4 части.
* В JASS-блок таблица частей ложится плоскими массивами
  (`HW_shopPartBase[idx]`, `HW_shopPartCount[idx]`,
  `HW_shopPartCatIdx/PartUnitId/PartCost[]` — сквозной индекс по всем частям
  всех товаров), заполняемыми в сгенерированном `HW_ShopDataInit`.
* `HW_ShopBuy` переписан: считает суммарную стоимость всех частей клика,
  **до** любого заказа проверяет `GetPlayerState(..,PLAYER_STATE_RESOURCE_
  GOLD) >= total` — если золота не хватает, ничего не покупается, игроку
  выводится сообщение с нужной суммой. Затем для каждой части отдельно
  находит ближайшее здание нужной категории (`HW_ShopFindShopUnit`,
  переиспользуется как есть — категория части такая же по смыслу, как и
  раньше "shopIdx" для целого товара) и, только если **все** части нашли
  здание, выдаёт по одному настоящему `IssueNeutralImmediateOrderById` на
  каждую (рецепт-свиток и каждый компонент — своим заказом на своей лавке,
  как и требовала задача). Если здание для какой-то части не нашлось —
  отмена целиком, ничего не заказывается (деньги ещё не потрачены, т.к.
  проверка идёт отдельным проходом до заказов).

### 2. Раскладка

Панель теперь **впритык к правому краю экрана** — `PANEL_RIGHT_X=0.80` без
отступа (`PANEL_MARGIN_RIGHT` убран), сразу под полосой очков
(`PANEL_TOP_Y=0.555`) и до верха командной панели (`PANEL_BOTTOM_Y=0.20`).
Заголовок блока — однострочный `TEXT`, ширина равна ширине сетки
(`HEADER_W = ICON_PITCH*4`, а не произвольная `COL_W-запас`, как раньше),
привязан TOP-LEFT к той же точке `(bx,by)`, что и сетка 4×3 под ним
(масштаб текста `0.55` через `BlzFrameSetScale` — тот же приём "сжать при
необходимости", раньше жёстко захардкожен, сейчас формально удовлетворяет
пункту задачи "shrink with BlzFrameSetScale if needed"). Иконки — `ICON`
теперь берётся как минимум из двух ограничений (по высоте блока и по
ширине столбца), т.е. **настолько крупные, насколько позволяет место**, а
не выведены только из вертикального бюджета, как в v3.

ASCII-таблица раскладки (значения — константы `shop_jass.py`, экранные
координаты 0..1, `y` растёт вверх, как в `BlzFrameSetAbsPoint`):

```
Экран (0,0)...(1,1), 4:3 UI-фрейм
                                                   PANEL_RIGHT_X=0.80 (край экрана)
                                                              |
  y=0.555  PANEL_TOP_Y ----------------------------------------+  <- полоса очков
           +----------------------------------------------------+
           | [X]                                                |  <- крестик закрытия (0.006 отступ)
           |  col0 (bx=0.007)   col1 (bx=0.1007)  col2 (bx=0.1943)|
           |  +-Header (0.0747 wide)-+  (x3, по одному на столбец)|
           |  [4x3 icon grid, ICON=0.0179, pitch=0.0187]         |
           |  ... 5 блоков на столбец (SHOPS_PER_COL=5) ...      |
           |  (BLOCK_PITCH=0.0658 между блоками одного столбца)  |
           +----------------------------------------------------+
  y=0.20   PANEL_BOTTOM_Y ---------------------------------------+  <- верх командной панели
           PANEL_W=0.28 (0.80-0.52), 3 колонки по COL_W=0.0933
```

Числовые константы (см. `shop_jass.py`): `PANEL_W=0.28`, `PANEL_H=0.355`,
`COL_W=0.0933`, `HEADER_W=0.0747`, `HEADER_H=0.007`, `ICON=0.0179`,
`ICON_PITCH=0.0187`, `BLOCK_PITCH=0.0658`, `BLOCK_H=0.0638`,
`GRID_H=0.056`. `ICON` теперь попадает в запрошенный диапазон
`~0.017–0.02` (в v3 было `~0.016` — чуть меньше из-за отступа панели,
который в v4 убран).

### 3. Тумблер "Shop"

По результатам предыдущего вида (кнопка легла чуть правее/ниже надписи
"SHOP" на командной панели HUD) координаты сдвинуты **влево на 0.012 и
вверх на 0.006**: было `TOGGLE_X0/Y0/X1/Y1 = 0.56/0.16/0.62/0.19`, стало
`0.548/0.166/0.608/0.196` (константы по-прежнему в верху `shop_jass.py`,
уже открыто экспонированы под этими именами — правка по задаче лишь меняет
значения). `TOGGLE_ALPHA` возвращён к `0` (полностью прозрачная кнопка) —
предыдущая полу-видимая (`alpha=40`) версия была временной мерой именно для
подбора этого смещения, задача явно просит вернуть альфу в 0 "once
positioned". Чат-команда `-shop` не тронута, продолжает работать.

Проверено `pjass` на копии карты в scratchpad (0 ошибок в собственном коде;
фоновый счёт 147 ошибок у `Blizzard_clean.j` не изменился), идемпотентность
(`--apply` дважды подряд — `+0` байт, `--undo --apply` дважды подряд —
второй раз `+0` байт) и сосуществование с блоком `HW_COOLDOWN_*`
(`cooldown-numbers --apply`, затем `shop-ui --apply`, `pjass` — снова 0
ошибок в собственном коде). Живым клиентом Warcraft III эта, четвёртая,
геометрия/механика в этой сессии не проверялась (в среде разработки нет
игрового клиента) — как и во всех предыдущих ревизиях этого файла.

## v3: настоящая покупка через Sellunits, невидимая-но-кликабельная кнопка, 3 столбца

По результатам живого прогона v2 (открылась, панель/кнопки видны правильно,
но: (а) покупка "Lothar's Edge" дала готовый предмет за 2800 золота — это
была лишь имитация из `UnitAddItemById`/`SetPlayerState`, а не настоящая
продажа лавкой; (б) невидимая кнопка "Shop" не ловила клики; (в) иконки были
слишком мелкими, а заголовки блоков — судя по скриншоту — рисовались
отдельным столбцом поверх сеток) внесены три правки:

1. **Покупка теперь идёт через настоящий механизм лавки (`Sellunits`), а не
   через подделку.** Клик по иконке больше не вызывает `UnitAddItemById` +
   `SetPlayerState` напрямую — вместо этого он делает ровно то же, что клик
   по товару в родной панели лавки: заказывает игроку продажу (`Sellunits`)
   у настоящего юнита-лавки картой (`IssueNeutralImmediateOrderById`), а
   дальнейшее — списание золота по `Units\UnitBalance.slk:goldcost`,
   создание настоящего предмета (через поле "Item Made" проданного юнита-
   обёртки — это штатный, не скриптовый механизм движка Warcraft III, тот же,
   что использует родная панель лавки) и попытку положить его в инвентарь
   ближайшего к лавке союзного юнита — делает сам движок, без единой строчки
   нашего JASS.
   * **Владелец лавок**: прочитан прямо из декомпилированного `war3map.j`
     карты — **все** 14 базовых лавок (и Radiant-, и Dire-копии) создаются
     как `CreateUnit(ra,'<код>',...)`, где `ra=Player(PLAYER_NEUTRAL_PASSIVE)`
     (переменная `X=PLAYER_NEUTRAL_PASSIVE`, затем `ra=Player(X)`, см. grep
     ниже). Значит используется именно
     `IssueNeutralImmediateOrderById(buyer, shopUnit, soldUnitTypeId)`, как и
     предполагала задача для нейтральных лавок — второй вариант
     (`IssueImmediateOrderById` для лавки, принадлежащей игроку команды) в
     этой карте не нужен, лавки не принадлежат игрокам команд.
   * **Order id = rawcode продаваемого юнита-обёртки** (`h076` и т.п., уже
     хранится в `HW_shopUnitId[idx]`) — это стандартная конвенция Warcraft
     III для `Sellunits` (order id продажи равен type id продаваемого юнита),
     отдельно искать номер приказа не потребовалось.
   * **Какой физический экземпляр лавки использовать**: у 13 из 14 категорий
     Radiant- и Dire-копия — это ОДИН И ТОТ ЖЕ rawcode юнита (внешний вид и
     характеристики одинаковы, отличается только размещение), и лишь у
     "Black Market" — два разных rawcode (`n12B` у Radiant, `n12N` у Dire).
     `collect_catalog` теперь сохраняет для категории все её rawcode
     построек (`cat['shop_codes']`, было и раньше — это уже собирал
     `workshop.py shops()`) в новый массив `HW_shopBuildingCode`. В момент
     покупки (`HW_ShopFindShopUnit`) перебираются все живые юниты
     `PLAYER_NEUTRAL_PASSIVE`, отбираются с подходящим типом и выбирается
     **ближайший к герою покупателя** — это выступает заменой понятия
     «лавка команды покупателя» без необходимости знать/парсить, какие
     номера игроков — Radiant, а какие — Dire (это глубоко зашито в
     обфусцированном скрипте карты и не читается по строкам надёжно): герой,
     стоящий у своей базы, всегда получит ближайшую версию лавки — то есть
     свою.
   * **Если герой не рядом ни с одной копией лавки**: отдельный откат на
     "курьера/фонтан" в этом файле НЕ реализован. Внимательный поиск по
     декомпилированному `war3map.j` (`grep -n "GetSoldUnit()\|EVENT_PLAYER_
     UNIT_SELL\b"`) не нашёл ни одного обработчика для обычной покупки
     предмета — все найденные `EVENT_PLAYER_UNIT_SELL`-триггеры относятся
     либо к экрану выбора/бана героя (система `Rt`/`Ban`+id, hero-tavern),
     либо к особым юнитам-лавки: курьер (`h085`), реинкарнация героя
     (`h0BV`/`h0DE`). Значит, если у этой карты вообще есть штатное
     «предмет падает на фонтан/курьера», это **встроенное поведение движка
     Warcraft III** для `Sellunits` без союзника в радиусе, а не отдельный
     скрипт карты, в который можно было бы дозаписаться — задокументировано
     как факт находки, а не придумано.
   * Секретная (`uC74`) и боковая (`u010`) лавки по-прежнему исключены в
     `collect_catalog` — их товары недоступны из этой панели.
2. **Кнопка "Shop" была полностью невидимой (`BUTTON` без фона) и не ловила
   клики** — судя по всему, `BUTTON`-фрейм без дочернего `BACKDROP` либо без
   назначенной текстуры в этом клиенте не получает событие
   `FRAMEEVENT_CONTROL_CLICK` надёжно. Исправлено: кнопка снова строится как
   везде в этом файле — `BACKDROP` (текстура кнопки, как у крестика закрытия)
   + `BUTTON`-ребёнок поверх, но с `BlzFrameSetAlpha(bg, 40)` — то есть едва
   заметная, а не полностью прозрачная, чтобы **сейчас** можно было увидеть,
   куда именно она легла, и подстроить `TOGGLE_X0/Y0/X1/Y1` (константы вверху
   `shop_jass.py`) по факту; альфа опускается до 0 отдельной правкой, когда
   смещение подтверждено вживую.
3. **Раскладка**: панель отодвинута от жёсткого правого края экрана
   (`PANEL_MARGIN_RIGHT=0.02`, `PANEL_RIGHT_X=0.78` вместо `0.80`); всё те же
   границы по высоте (низ полосы очков `0.53` — верх командной панели
   `0.20`). Блоки теперь **в три столбца по пять** (`BLOCK_COLS=3,
   SHOPS_PER_COL=5`, вместимость 15 ≥ 14 лавок) вместо двух по семь — при
   том же вертикальном бюджете это даёт заметно более крупные иконки
   (`ICON≈0.016`, было `≈0.0104`, ближе к запрошенным `0.017-0.02`).
   Заголовок блока и его сетка гарантированно используют одну и ту же `bx`
   (левый край столбца) — заголовок рисуется первым по `(bx,by)`, сетка сразу
   под ним по `(bx, by-HEADER_H-HEADER_GAP-...)`, так что заголовок не может
   оказаться в «отдельном столбце» по построению; если на скриншоте v2 они
   расходились — это не воспроизведено логическим разбором текущего кода
   (не проверено живым клиентом заново в этой сессии, клиента здесь нет).

Проверено `pjass` на копии карты в scratchpad (0 ошибок в собственном коде,
тот же фоновый счёт 147 ошибок/51 строка у `Blizzard_clean.j`, что и раньше),
идемпотентность (повторный `--apply` — `+0` байт), откат (`--undo --apply`) и
сосуществование с `HW_COOLDOWN_*` — как и в предыдущих ревизиях. Живым
клиентом эта, третья, геометрия и новая механика покупки в этой сессии не
проверялись (нет клиента в среде разработки) — следующий живой прогон должен
подтвердить: (1) реальную покупку по правильной цене/с правильным предметом,
(2) что кнопка "Shop" теперь ловит клик (и на каком именно месте она видна
при alpha=40, чтобы подправить `TOGGLE_*`), (3) что заголовки/сетки не
перекрываются.

## v2: колонка у правого края экрана, без вкладок/страниц

По результатам второго живого прогона (`v2` из первой ревизии этой заметки —
панель со вкладками и двумя страницами — открылась и заголовок/вкладки были
видны, но **фон панели остался сплошным зелёным**, то есть
`human-options-menu-background.blp` в этом клиенте недоступен как текстура
для голого `BACKDROP` без объявления в TOC/FDF, хотя тот же путь как будто
использовался в самом первом прогоне) макет полностью переделан по прямому
требованию задачи — **не вкладки/страницы, а колонка у правого края экрана,
как магазин в Dota 2**, все 14 базовых лавок показаны одновременно:

* **Расположение панели** — `shop_jass.PANEL_*` (см. константы вверху
  `shop_jass.py`): `FRAMEPOINT_TOPRIGHT` в точке (0.80, 0.53) — чуть ниже
  полосы очков; высота до y=0.20 — верх командной панели (высота 0.33,
  ширина 0.26). Открытие — мгновенное (без анимации выезда), просто
  `BlzFrameSetVisible`, как и раньше.
* **Все 14 лавок — сеткой блоков, без вкладок и без страниц**: два столбца
  по `SHOPS_PER_COL=7` блоков (константа в `shop_jass.py`, ровно совпадает с
  числом базовых лавок после свёртки Radiant/Dire дублей — `14 = 2×7`).
  Каждый блок — маленький ASCII-заголовок (имя лавки) + сетка 4×3 иконок в
  **тех же ячейках, что и в родной панели покупки лавки** (`Buttonpos`
  проданного юнита-обёртки: `col,row → row*4+col`; ячейки без товара —
  пустые). Подпись цены под иконкой убрана по требованию задачи — цена и имя
  остались в тултипе (`BlzFrameSetTooltip`).
* **Размер иконки уменьшен до ~0.0104** (константа `ICON` в `shop_jass.py`,
  выведена арифметически из `PANEL_H`, `TOP_MARGIN`, `SHOPS_PER_COL=7` и трёх
  строк на блок — см. комментарий у `ICON` в коде) — заметно меньше
  подсказанных в задаче «~0.018–0.024». Это осознанное отступление: два
  требования задачи входят в противоречие («не более ~0.16 от низа» +
  «никаких вкладок/страниц» с одной стороны, «иконки ~0.018-0.024» с другой)
  — семь блоков по три строки крупных иконок физически не помещаются по
  высоте между полосой очков и командной панелью без прокрутки/страниц;
  приоритет отдан первому (не залезать на HUD, не листать страницы), иконка
  уменьшена ровно настолько, чтобы 7×2=14 блоков влезали без остатка
  (`7 * BLOCK_PITCH == BODY_H` проверено в коде).
* **Кнопка "Shop" — теперь невидимая кнопка поверх штатной надписи "SHOP"**
  на командной панели HUD, а не отдельная видимая кнопка (первая версия
  рисовала свою кнопку поверх командной панели, что было явно указано как
  дефект). Координаты — константы `TOGGLE_X0/Y0/X1/Y1` вверху `shop_jass.py`
  (изначально `0.56..0.62 × 0.16..0.19`, ориентировочно, для подгонки под
  живой клиент), кнопка без фона и без текста (`BlzCreateFrameByType("BUTTON",...)`
  напрямую на `ORIGIN_FRAME_GAME_UI`, `BlzFrameSetAbsPoint(FRAMEPOINT_BOTTOMLEFT,...)`).
  Чат-команда `-shop` работает как раньше.
* **Текстуры фона заменены**: панель и подложка блок-заголовков —
  `UI\Widgets\ToolTips\Human\human-tooltip-background.blp` (тултип-фон,
  используется многими системами как безопасный "голый" backdrop);
  кнопка закрытия — `UI\Widgets\Console\Human\human-console-button-background.blp`.
  Обе — не проверены живым клиентом из этой среды (клиента здесь нет);
  если фон снова окажется зелёным/пустым, следующий шаг — `BlzFrameSetAlpha`
  на сплошной цвет вместо текстуры, или иконка `BTN*`-стиля как временный
  фон (см. обсуждение в задаче).
* **Без страниц/вкладок — контент статичен**: все иконки создаются и сразу
  заполняются один раз в `HW_ShopBuild` (`HW_ShopDataInit` → один проход по
  всем лавкам и ячейкам), никакого `HW_ShopShowPage`/`HW_ShopShowCat` больше
  нет. Значит **общая для всех игроков "текущая страница" из v1 (см. ниже)
  больше не проблема** — открыто/закрыто всё ещё персонально
  (`GetLocalPlayer()`), а показываемый контент теперь одинаков всегда и для
  всех, не переключается.
* Раскладка проверена только `pjass` (0 ошибок в собственном коде, тот же
  фоновый счёт 147/51, что и раньше — см. «Как попробовать» ниже); живым
  клиентом эта, вторая, геометрия в этой сессии не проверялась (сообщение
  выше про "второй прогон" описывает результат **предыдущей** правки,
  сделанной другой сессией/раньше в этом же треде задачи).

инъекция). План и обоснование выбора варианта A (чистый JASS, без FDF/TOC,

(`common_clean.j Blizzard_clean.j <патченный war3map.j>` — 0 ошибок в самом
патченном файле; 147 ошибок `Blizzard_clean.j` — это фон среды, тот же счёт

первый прогон в игре и правки по его результатам).

## Первый прогон в игре (WC3 1.31.1) и правки

Первая версия открывалась и покупка работала, но с тремя визуальными
дефектами, все три исправлены:

1. **Фон панели был сплошной ярко-зелёный** — панель-`BACKDROP` создавалась
   без текстуры (`BlzFrameSetTexture` не вызывался). Исправлено: панель
   получает `UI\Widgets\EscMenu\Human\human-options-menu-background.blp`
   (штатная текстура клиента 1.31, не требует файлов в MPQ карты).
2. **Заголовок показывал "HW Shop (????????)"** — в JASS-код был зашит
   кириллический текст `"HW Shop (прототип)"`; шрифт клиента не смог его
   показать. Исправлено: заголовок теперь чисто ASCII — `"HW Shop"`.
   Дополнительно (на случай другой карты, где текст лавки/товара из
   *.txt файлов сам не ASCII — latin1/cp1251 mix в данных карты, а не в
   коде): `shop_jass.collect_catalog` теперь проверяет каждое название
   категории (`shop['name']`) и каждое название товара (`w.name(u,
   'UnitFunc')`) на то, что все символы — ASCII (`_is_ascii`); если нет —
   категория получает запасное имя `"Shop N"` (N — порядковый номер после
   фильтрации пустых категорий), а товар — `"Item <rawcode предмета>"`.
   Тем самым тултип (первая строка — `HW_shopName[idx]`) и сообщения покупки
   гарантированно отображаемы. **На тестовой карте (`test_shop.w3x`, 14
   категорий, 160 товаров) все имена и так были ASCII** — реальной причиной
   "????????" был только зашитый русский текст заголовка, но защита от
   非-ASCII данных каталога добавлена по прямому требованию задачи.
3. **Вкладки категорий были невидимы (без текста, без фона)** — вкладки (и
   кнопка-крестик, и кнопка-переключатель "Shop") создавались как одиночный
   `GLUEBUTTON` с текстом через `BlzFrameSetText` и без собственной текстуры;
   в клиенте 1.31 такой фрейм ничего не рисует. Исправлено: для каждой
   вкладки, для крестика и для кнопки "Shop" теперь три фрейма — `BACKDROP`
   (текстура `UI\Widgets\EscMenu\Human\human-options-button-background.blp`)
   + дочерний `TEXT` (подпись, `BlzFrameSetAllPoints` на весь backdrop) +
   `BUTTON` поверх (тоже на весь backdrop, ловит клик, сам невидим/без
   текстуры). Активная вкладка подсвечивается изменением текста на
   `"[Имя]"` (`HW_ShopShowCat` теперь перед перерисовкой сетки проходит по
   всем вкладкам и переключает их подпись).

Заодно панель сделана компактнее и вкладки — в две строки по 7 (было: одна
строка на все 14, слишком узко — `0.48/14 ≈ 0.034` на вкладку): раскладка
вкладок теперь фиксированная сетка 7×2 (`col=i mod 7`, `row=i div 7`,
`tabw=0.48/7`), сетка товаров (6×4=24, без изменений) сдвинута вниз, чтобы
не пересекаться со второй строкой вкладок; высота панели выросла с 0.42 до
0.44 (ширина не менялась — 0.50, по-прежнему помещается на экран). Логика
покупки не тронута.

## Что реализовано

* Сбор каталога (`shop_jass.collect_catalog`): 14 базовых категорий
  (`workshop.py shops()`, без потайной `uC74` и боковой `u010`), их товары —
  из `item_list()` (юнит-обёртка лавки → rawcode предмета), цена — из
  `Units\UnitBalance.slk:goldcost` для юнита-обёртки (совпадает со
  стандартными ценами Dota; для нескольких товаров, где это поле было
  пустым, — резервный вариант: `ItemData.slk:goldcost` любого предмета того
  же семейства), иконка — `Art=` юнита-обёртки как есть (тот же путь, что
  уже показывается на карточке лавки в игре, включая `WC3DotaHQTest\A\...`
  для карт с внешним мод-путём).
* Один блок JASS (`HW_SHOP_GLOBALS_BEGIN/END`, `HW_SHOP_BEGIN/END`,
  `HW_SHOP_CALL`), инъецируется/откатывается идемпотентно, тем же паттерном,
  что `cooldown_jass.py` (`HW_COOLDOWN_*`), и сосуществует с ним — оба блока
  проверены вместе (пример в репозитории: сначала `cooldown-numbers --apply`,
  потом `shop-ui --apply`, `pjass` — 0 ошибок своего кода).
* UI (`BlzCreateFrameByType`, без FDF): панель-`BACKDROP` со штатной
  текстурой `human-options-menu-background.blp`, заголовок (ASCII), сетка
  6×4=24 переиспользуемых слотов (`BACKDROP`-иконка + `BUTTON` поверх для
  клика + `TEXT`-цена под иконкой + отдельный `TEXT`-фрейм как тултип —
  `BlzFrameSetTooltip`). Кнопка-крестик закрытия, до 14 вкладок-категорий (в
  две строки по 7) и кнопка-переключатель "Shop" (всегда на экране) — все
  три вида кнопок собраны одинаково: `BACKDROP` с текстурой
  `human-options-button-background.blp` + дочерний `TEXT` с подписью
  (`BlzFrameSetAllPoints` на весь backdrop) + `BUTTON` поверх, тоже на весь
  backdrop, ловит клик. Активная вкладка подсвечивается текстом `"[Имя]"`.
* Переключение окна — чат-командой `-shop` (зарегистрирована на всех
  `bj_MAX_PLAYER_SLOTS` игроков) и кнопкой `Shop`; видимость меняется только
  `if GetLocalPlayer()==p then ... endif` вокруг `BlzFrameSetVisible` —
  никаких хендлов внутри не создаётся, поэтому это не может привести к
  рассинхрону, и у каждого игрока получается своё "открыто/закрыто".
* После любого клика — `BlzFrameSetEnable(f,false)` + `(f,true)` (снятие
  фокуса, чтобы клавиатура не перехватывалась кнопкой).
* Покупка (`HW_ShopBuy`): проверка `GetPlayerState(..,PLAYER_STATE_RESOURCE_GOLD)`,
  списание `SetPlayerState`, `UnitAddItemById` на первого героя игрока
  (`GroupEnumUnitsOfPlayer` + `IsUnitType(.., UNIT_TYPE_HERO)`); если предмет
  не влез (`UnitAddItemById` вернул `null`) — золото возвращается. Сообщения
  игроку через `DisplayTextToPlayer`.

## Сознательно упрощено / не реализовано

* **Покупка не имитирует штатную продажу лавки** (`EVENT_PLAYER_UNIT_SELL`,
  `a2v`/`aHv` из `docs/SHOP_UI_PLAN.md` §2.3). План предлагал это как основной
  путь, но пометил номера order id для `Sellunits` как неподтверждённые без
  живого клиента (§6) — в задаче на этот случай прямо разрешён запасной
  вариант («fall back to `UnitAddItemById`... document the recipe
  implications»), он и выбран. Следствия: **если у героя нет героя рядом
  (например, только что умер и ещё не переродился)** — покупка не проходит
  и просто отменяется с сообщением, тогда как в штатной системе предмет упал
  бы у фонтана/на курьера. **Постройка предмета через курьера/на землю у
  фонтана не реализована.**
* **Дерево рецептов** (компоненты Aghanim's Scepter и т.п., `ItemData.slk`
  поля `requires`) не читается и не показывается в тултипе — тултип сейчас
  только имя + цена. План относил это к отдельной задаче с данными (§2.4);
  в первом прототипе не тронуто.
* **Категория — общая, а не персональная.** Открыто/закрыто окно — у каждого
  игрока своё (см. выше), но переключение вкладки перерисовывает общие
  фреймы сетки и общую хэш-таблицу "фрейм → индекс товара" без проверки
  `GetLocalPlayer()` — специально, чтобы обработчик покупки читал одинаковый
  индекс на всех клиентах (иначе рассинхрон между тем, что видит кликнувший,
  и тем, что вычисляют остальные клиенты). Значит: если несколько игроков
  одновременно откроют магазин, переключение вкладки одним игроком
  переключит и то, что видят остальные открывшие окно в этот момент. Для
  прототипа это приемлемо; для многопользовательской версии нужно либо
  держать по 24 слота на игрока (дороже по фреймам), либо использовать
  `BlzFrameSetTexture`-only обновление без общей хэш-таблицы (усложняет
  разбор клика).
* **Секретная (`uC74`) и боковая (`u010`) лавки не входят в окно** — по
  прямому требованию задачи и плана, остаются обычными зданиями.
* **Раскладка/вёрстка проверена в игре один раз (WC3 1.31.1)** после правок
  выше (фон панели, ASCII-заголовок, backdrop+text+button на вкладках):
  координаты (`BlzFrameSetAbsPoint`/`BlzFrameSetPoint`, ячейки 0.058×0.058,
  панель 0.50×0.44, вкладки — сетка 7×2) не переигрывались повторно — то
  есть сам факт "не зелёный фон / виден текст на вкладках" не проверен
  повторно этой сессией (нет живого клиента в среде разработки), только
  `pjass`. Возможны более тонкие огрехи вёрстки (обрезка длинных названий
  категорий вроде "Cache of the Quel'thelan" при масштабе текста 0.70).
* Строковые типы фреймов (`"BACKDROP"`, `"BUTTON"`, `"TEXT"`) и то, что
  `BlzFrameSetTexture` действительно подхватывает путь вида
  `WC3DotaHQTest\A\...` (внешний мод-путь, а не файл из MPQ карты) в рантайме
  клиента для иконок товаров, — предположение по аналогии с тем, как эта же
  строка уже используется картой для командной панели лавки; `pjass` типы
  строк не проверяет содержательно (это просто `string`), так что ошибка тут
  не будет поймана статически. Панель и кнопки теперь используют только
  штатные текстуры клиента (`UI\Widgets\EscMenu\Human\...`), подтверждённые
  первым прогоном в игре — это уже не предположение.

## Как попробовать

```zsh
export HERO_WORKSHOP_GAME_ROOT=/path/to/game
export HERO_WORKSHOP_MAP=/path/to/test_copy.w3x   # НЕ оригинал
python3 map_fix.py shop-ui --apply
```

Сначала можно применить `python3 map_fix.py cooldown-numbers --apply`, чтобы
проверить сосуществование обоих блоков (так и было проверено в этой сессии).
Откат: `python3 map_fix.py shop-ui --undo --apply`. Валидация синтаксиса без
живого клиента:

```zsh
pjass common_clean.j Blizzard_clean.j <war3map.j из карты после инъекции>
```

## Риски (перенесено/уточнено из `docs/SHOP_UI_PLAN.md` §6)

* Нет `BlzGetAbilityId`/`BlzFrameIsVisible` в рантайме 1.31 — код их не
  использует (только `HaveSavedInteger` для сравнимой проверки хэш-таблицы,
  и локальный булев `HW_shopLocalOpen` вместо чтения видимости фрейма).
  `BlzGetTriggerPlayer` в `common_clean.j` тоже не объявлен как отдельный
  native — везде используется обычный `GetTriggerPlayer()` (работает и для
  чат-события, и для `FRAMEEVENT_CONTROL_CLICK`, судя по объявлению
  `native GetTriggerPlayer takes nothing returns player` без ограничения по
  типу события).
* Иконки некоторых товаров использовали общий/пустой fallback ранее в других
  инструментах (`icon_info`) — в собранном каталоге (160 товаров) таких не
  было (`missing_icon=0` на тестовой копии карты), но на другой версии карты
  число может отличаться — `map_fix.py shop-ui` (без `--apply`) печатает план
  и не упадёт молча на отсутствующей иконке, а просто пропустит товар без
  `Art=` (см. `collect_catalog`), поэтому расхождение будет видно по
  количеству товаров в выводе.
