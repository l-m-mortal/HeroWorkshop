# Магазин-окно в стиле Dota 2: анализ и план (черновик, ничего не применялось)

Карта: DotA 6.85ne14, движок Warcraft III 1.31.1 (macOS), скрипт SLK/txt +
обфусцированный `war3map.j`. Внедрение — чистый JASS-блок по образцу
`cooldown_jass.py` (глобалы → функции перед `main` → один вызов в конце `main`,
идемпотентно, откат меткой-комментарием). vJASS/Lua недоступны — карта их не
поддерживает, JassHelper в пайплайн не встроен.

**Вывод:** TasItemShop и всё его окружение рассчитаны на vJASS (`.j`
компилируется JassHelper'ом в обычный JASS с префиксами `Tas...`, но
исходники и API системы — это структуры, интерфейсы, модули vJASS) либо на
Lua. Готовый релиз **нельзя** взять и вставить как чистый JASS: придётся либо
вручную «развернуть» структуры в глобальные массивы (много работы, риск
ошибок, и правовой вопрос переиспользования чужого кода без атрибуции), либо
написать своё окно с нуля на чистом JASS, используя только сами Frame-натвы
(они рассчитаны на 1.31+ и это чистые JASS-функции, никакого vJASS не
требуют). **Рекомендация ниже — писать своё, минимальное окно**, вдохновляясь
структурой TasItemShop (категории → сетка иконок → тултип → клик = покупка),
но кодом из наших же инструментов (`cooldown_jass.py` уже показывает, что
такой Frame-код у нас прекрасно работает на этой карте).

Проверено локально по валидатору pjass (`common_clean.j` рядом с pjass) —
следующие нужные нативы объявлены и используются в патченном 1.31 `common.j`

`BlzCreateFrame`, `BlzCreateFrameByType`, `BlzFrameSetTexture`,
`BlzFrameSetVisible`, `BlzFrameIsVisible`, `BlzTriggerRegisterFrameEvent`,
`BlzFrameSetPoint`, `BlzFrameSetAbsPoint`, `BlzFrameSetText`,
`BlzFrameSetSize`, `BlzFrameSetScale`, `BlzFrameSetEnable`,
`BlzFrameSetTooltip`, `BlzFrameSetModel`, `BlzFrameSetSpriteAnimate`,
`BlzGetTriggerFrame`, `BlzGetTriggerPlayer`, `BlzLoadTOCFile`,
`FRAMEEVENT_CONTROL_CLICK`. `BlzGetAbilityId` тоже объявлен в `common.j`, но
по опыту `cooldown_jass.py` в рантайме 1.31 он не работает (поэтому там
способности ищутся перебором id) — для магазина это не важно, он не нужен.

## 2. Как лавки работают в этой карте сейчас

### 2.1. Какие лавки есть

`workshop.py Workshop.shops()` находит юнитов с непустым `Sellunits`, у
которых распродаваемые коды — юниты (не абилки/предметы) и их ≥4: это ровно
лавки-дома. В текущей карте таких **17** (при чтении карты через
`HERO_WORKSHOP_MAP=.../Dota_Radiant_Terrain_Fix_v4.w3x`):

```
e025  Ancient of Wonders        h076,h02A,h02F,h028,h02B,h029,...
n00W  Ancient Weaponry          h03C,h03E,h03F,h03J,h03D,h02S,...
n00V  Arcane Sanctum            h03M,h03X,h02Y,h07T,h038,h039,...
n12B  Black Market              h0EN,n12C,h0DY,n12D,n12E,n12F,...
n12N  Black Market (вторая сторона, свой rawcode юнита)
hC95  Cache of the Quel'thelan  h087,h01M,h01X,h01K,h021,h01R,...
... (ещё 11 записей: секретная лавка uC74, боковая u010, лавки предметов
    силы/поддержки/etc с двумя копиями на команду — Sentinel/Scourge)
```

Это классическая структура DotA 6.8x: **не один магазин**, а набор
«категорийных» домов-лавок (у каждой команды свой rawcode, но одинаковый
список товаров). «Единое окно по категориям» в терминах задачи — это как раз
объединение всех этих `Sellunits`-списков в одну сетку с разделами.

`workshop.py item_list()` уже строит нужную группировку: для каждой лавки
берётся список продаваемых юнитов-обёрток (`h0xx`/`n0xx`), их имя приводится
к «семейству предмета» (`item_base_name`, срезает `(Hero)`, `Level N` и
т.п.), и семейство связывается и с этими юнитами-обёртками (что видно в
магазине — иконка юнита), и с реальными rawcode'ами предметов (что окажется
в инвентаре). Т.е. **сопоставление «товар лавки → predmet-код» у нас уже
есть на уровне Python-инструмента** — этот же алгоритм (перенесённый в JASS
как таблица id→id, сгенерированная во время инъекции, ровно как
`cooldown_jass.ids_function`) даст фрейм-магазину список «что показывать и
что выдавать».

### 2.2. Стоимость и иконки

* Цена — `ItemData.slk` (или соответствующий txt), поле `goldcost`; читается
  тем же `workshop.txt`/slk-парсером, что и остальные данные карты.
* Иконка — `Art=`/`art=` в `ItemFunc.txt` (или blp/иконка из `icon_info`),
  уже используется `workshop.py` (`icon_info('item:' + code)` /
  `icon_info('unit:' + code)`), в примере выше видно реальные пути вида
  `WC3DotaHQTest\A\ReplaceableTextures\CommandButtons\BTNAegis...blp`.
* Рецепты — семейство предмета включает базовый предмет и рецепт как
  отдельный `codes`/`variants` (пример: `Aghanim's Scepter` и `Aghanim's
  Scepter Recipe` — это два *отдельных* семейства в текущей группировке по
  имени, значит дерево рецептов придётся строить отдельно — см. §2.4).

### 2.3. Как деньги/покупка обрабатываются сейчас (`war3map.j`)

Стандартный native-магазин Warcraft III: лавка — нейтрально-враждебное здание
с `Sellunits`; когда игрок покупает товар, **движок сам снимает золото**
(по `goldcost` юнита-обёртки) и генерирует событие
`EVENT_PLAYER_UNIT_SELL`. Никакого ручного списания в скрипте карты для этого
шага нет — оно встроено в движок.

Обработчик события (найден по `GetSoldUnit()`/`GetSellingUnit()` в
`war3map.j`, ~15900–16030 строки):

```jass
function a2v takes nothing returns boolean          // главный колбэк продажи
    local unit u = GetSoldUnit()                    // купленный юнит-обёртка
    local player p = GetOwningPlayer(u)
    local integer id = j1(u)                        // индекс товара по типу юнита
    call ShowUnit(u,false)
    call UnitApplyTimedLife(u,'BTLF',2)              // обёртка скрывается и умирает
    call alv(p,A0(id))                               // побочные счётчики
    set x=amv(GetSellingUnit(),u)                    // координаты выдачи (фонтан/лавка)
    set y=apv(GetSellingUnit(),u)
    call aHv(p,u,GetSellingUnit(),A0(id),x,y,0,0)     // фактическая выдача предмета
    return true
endfunction
```

`aHv` (строки 15445–15507) — фактическая «выдача»: если герой/курьер (`d`)
найден рядом с лавкой — `UnitAddItemById(d, ae[aJv])`, предмет сразу в руки;
если нет — `R1(de[aJv],x,y,p,false,0)` создаёт предмет **на земле в фиксированной
точке фонтана команды**; отдельные ветки — предметы-стаки (заряды через
`SetItemCharges`) и предметы с проверкой рецепт-контейнера (`w0`/`W0`).

`R1` (строки 6724+) не создаёт предмет мгновенно, а **ставит one-shot таймер**
(`TriggerRegisterTimerEvent(..,0,false)` + `SaveInteger/.../SavePlayerHandle`
в хэш-таблицу `HY`), который в следующем такте вызывает создание предмета —
видимо, защита от коллизий/дублей при одновременных покупках. `d` — это
искомый герой/курьер в радиусе лавки (см. `aGv`, ищет юнита игрока рядом);
если героя у лавки нет, `amv/apv/aPv/aqv` подставляют **фиксированные
координаты фонтана каждой команды** (`-7488,-7168` и `7040,6400` для
Sentinel/Scourge — видно прямо в коде), то есть **механика "купил без героя →
предмет падает у фонтана" уже реализована штатно**, и есть отдельный
персональный "курьер"-хэндл на игрока (`SaveUnitHandle(qe,GetHandleId(p),
'COUR',...)` и второй слот `'COUR'+1` — это инвентарный юнит, которому
переигрывается способность `AInv`, т.е. предмет туда действительно кладётся
в инвентарь курьера/стэша, а не просто падает на текстуру).

Рецепты: `w0(JT)`/`W0(JT)` — два жёстких списка id-типов (константы `GG`,
`tF`, `lF`, ... — обфусцированные локальные имена globals, не rawcode'ы) —
судя по веткам (`CreateItem`+`UnitAddItem` vs `UnitAddItemById`+`charges`),
один список — предметы-стаки (заряды), второй — что-то вроде «доп.
контейнер»/рецепт-в-виде-отдельного-объекта. Комбинирование самих
компонентов в готовый предмет — стандартный движковый рецепт-механизм
Warcraft III (recipe-абилки на предметах, `ITEM_TYPE_...`), в это наш магазин
вмешиваться не должен и не будет — рецепты по-прежнему собираются игроком
через штатное перетаскивание предметов друг на друга в инвентаре.

**Важный вывод:** механизм «купить → золото снято → предмет либо герою, либо
на землю у фонтана/курьеру» уже полностью существует и рассчитан именно на
покупку **через продажу юнита-обёртки лавкой** (`IssueSellOrder`/клик по
иконке лавки, что технически и есть `IssueImmediateOrder`-подобная команда).
Самый безопасный способ «нажать в новом окне = купить» — **дать той же самой
лавке приказ продать нужного юнита-обёртку игроку-инициатору**, тогда сработает
весь существующий пайплайн (списание золота, `a2v`, `aHv`, курьер/фонтан,
счётчики `alv`) без единой правки старого кода.

### 2.4. Дерево рецептов

Прямого рецепт-дерева (что из чего собирается) в читаемом виде в скрипте нет
(эта логика в основном в Object Editor — предмет-рецепт с абилкой
"Item Recipe" + список требуемых предметов, хранится в `ItemData.slk` полях
`requires`/`nreq` или аналогичных, доступных через тот же slk-парсер, что и
`goldcost`). План: не пытаться визуализировать рецепт-дерево вычислением из
скрипта, а прочитать его прямо из `ItemFunc.txt`/`ItemData.slk` (поля
requirements) точно так же, как `workshop.py` уже читает `Art`/`goldcost` —
это чистая работа с данными, отдельная от вопроса о фреймах.

## 3. Два варианта реализации

### Вариант A — чистый JASS, фреймы `BlzCreateFrameByType` (без FDF/TOC)

*Идея.* Всё окно строится в рантайме через `BlzCreateFrameByType` (типы
`BACKDROP`, `GLUEBUTTON`, `TEXT`, `SPRITE` — их иконки/текстуры задаются
`BlzFrameSetTexture`), точь-в-точь как `cooldown_jass.py` уже строит текстовые
фреймы над кнопками. Никаких новых файлов в MPQ, всё — один блок JASS,
инъецируемый тем же `map_fix.py`-паттерном (globals/functions/main call,
идемпотентно, с меткой `HW_SHOP_BEGIN/END` для отката).

*Шаги:*
1. Python-скрипт (`shop_jass.py`, по образцу `cooldown_jass.py`) на этапе
   сборки карты собирает данные: список категорий (по числу/именам лавок из
   `shops()`), товары каждой категории (`item_list()` + фильтр «это базовая
   лавка, не секретная/боковая»), для каждого — rawcode юнита-обёртки лавки,
   rawcode предмета, цену (`ItemData.slk:goldcost`), путь иконки.
2. Генерируется JASS-таблица (аналог `ids_function`): массивы
   `HW_shopUnit[]`, `HW_shopItem[]`, `HW_shopCost[]`, `HW_shopIcon[]` (строка
   пути иконки для `BlzFrameSetTexture`), `HW_shopSeller[]` (rawcode
   лавки-здания, которая реально продаёт этот товар — нужно для приказа
   продажи).
3. При инициализации (`main`, один раз) создаётся дерево фреймов: одна
   кнопка на игровом UI (`ORIGIN_FRAME_...` или консольная кнопка через
   `BlzCreateFrameByType("GLUEBUTTON",...)`, размещённая, например, рядом с
   миникартой) — по клику открывает/закрывает панель магазина
   (`BlzFrameSetVisible`). Панель — `BACKDROP` на весь экран/часть экрана,
   внутри вкладки-категории (кнопки переключения) и сетка иконок-кнопок
   (`GLUEBUTTON` с `BlzFrameSetTexture` = иконка предмета, `BlzFrameSetText`
   или `BlzFrameSetTooltip` = имя + цена).
4. Клик по иконке (`BlzTriggerRegisterFrameEvent(t, btn,
   FRAMEEVENT_CONTROL_CLICK)`), в обработчике: `BlzGetTriggerPlayer()` +
   `BlzGetTriggerFrame()` → определить, какой индекс товара нажат (по
   заранее сохранённому в hashtable сопоставлению `frame handle id → индекс`,
   тот же приём, что `SaveInteger(HY, GetHandleId(frame), ...)` в оригинале
   карты).
5. **Покупка = не ручная выдача предмета, а имитация штатной покупки**:
   найти в мире (или создать скрытого, если такого пока нет) юнита-обёртку
   нужного типа, принадлежащего лавке-продавцу
   (`CreateUnit(GetOwningPlayer(лавка), HW_shopUnit[i], x, y, 0)` рядом со
   зданием, invisible/locust), и отдать игроку приказ
   `IssueTargetOrder(герой_или_курьер, "sell", unitObertka)` **или** прямой
   вызов родного триггера продажи, если он публично зарегистрирован
   (`TriggerEvaluate` не нужен — простая продажа юнита между союзными
   юнитами вызывает `EVENT_PLAYER_UNIT_SELL` штатно). Это даёт: списание
   золота по правилам движка (не нужно самим проверять баланс — если золота
   не хватает, продажа просто не пройдёт), срабатывание `a2v`/`aHv` без
   изменений в старом коде, и штатную доставку — герою в руки или на землю
   у фонтана/курьеру, если героя рядом с лавкой нет физически (что уже
   сделано в `aHv`/`amv`/`apv`).
   * Технически: у зданий с `Sellunits` каждая позиция списка имеет свой
     order id (обычно `sellunit1..sellunit6` по порядку списка) —
     `IssueImmediateOrderById` от лица здания на этот order воспроизводит
     ровно штатную покупку по клику. Это нужно подтвердить опытно на
     тестовой карте (номера зависят от того, как WC3 их генерирует).
   * Запасной путь, не зависящий от нумерации order id: временно создать
     невидимого юнита-обёртку нужного типа у здания-продавца, принадлежащего
     игроку, и сразу `IssueTargetOrder(герой, "sell", тот_юнит)` — это
     гарантированно порождает `EVENT_PLAYER_UNIT_SELL` 1-в-1 как ручная
     покупка, без выяснения order id. В WC3 покупка по клику не требует,
     чтобы герой физически стоял у здания (только чтобы был выделен и
     принадлежал игроку) — значит и триггерный вызов не должен требовать
     близости; это тоже нужно подтвердить тестом на реальном клиенте.
6. Один и тот же UI должен быть у каждого игрока локально — фреймы **не
   синхронизируются сами**, а `FRAMEEVENT_CONTROL_CLICK` в JASS-триггере
   срабатывает **у всех игроков одновременно** (это триггерное событие
   движка, не локальное отображение), поэтому обработчик обязан сверять
   `BlzGetTriggerPlayer()` и оперировать только с этим игроком, тогда как
   создание/показ самих фреймов допустимо делать глобально при старте карты
   (не через `GetLocalPlayer()`), чтобы избежать десинка (десинк бывает,
   когда что-то, видимое одному игроку, читается остальными как разное
   состояние — здесь состояние строго одинаковое у всех: одна и та же
   таблица товаров).

*Плюсы:* не трогает MPQ-структуру, идемпотентно, откатывается одной командой
как `cooldown-numbers --undo`, минимальный риск сломать существующие
триггеры (используем их же), укладывается в текущий пайплайн `map_fix.py`.

*Минусы:* без FDF внешний вид фреймов менее гибкий (`BACKDROP`/`GLUEBUTTON`
дают базовый набор свойств; сложная вёрстка типа тултипов с несколькими
строками текста и рамкой рецепта потребует много ручных под-фреймов); текст
жёстко из кода, шрифты/цвета — то, что даёт `TEXT`-фрейм.

### Вариант B — свои FDF + TOC файлы в архиве карты

*Идея.* Добавить в MPQ карты `war3mapImported\HW_Shop.fdf` (описание внешнего
вида: шаблоны фреймов, как в стандартных `UI\FrameDef\...`) и `.toc`
(перечисляет fdf-файлы для `BlzLoadTOCFile`), при инициализации —
`BlzLoadTOCFile("war3mapImported\\HW_Shop.toc")` и
`BlzCreateFrame("HW_SHOP_MAIN", ..., 0, 0)` по имени шаблона из FDF. Логика
клика/покупки — тот же JASS-код, что в варианте A.

*Плюсы:* более гибкая, декларативная вёрстка (много вложенных
BACKDROP/иконок/текста одним файлом, легче поддерживать зрительный стиль
близкий к Dota 2), не нужно вручную городить дерево фреймов из десятков
вызовов `BlzCreateFrameByType`.

*Минусы:* карта — SLK/txt-базис без `w3u/w3t`; добавление новых файлов в MPQ
уже делает `workshop.py`/`map_fix.py` (например, `hq-doodads` кладёт модели и
текстуры), значит технически это решаемо тем же способом (`w.changes[path] =
data; w.commit()`), но FDF — незнакомый карте формат: риск ошибки в
синтаксисе FDF, который трудно предварительно провалидировать (в отличие от
JASS, для которого есть pjass) — ошибки в FDF на 1.31 macOS часто тихие (фрейм
просто не появляется), отладка сложнее. Плюс TOC/FDF почти всегда пишут и
тестируют в редакторе (World Editor) с реальным клиентом — в этом пайплайне
нет доступа к живому клиенту WC3 для итеративной проверки вёрстки, только
pjass-валидация синтаксиса JASS.

### Рекомендация

**Вариант A.** Основания:
* Соответствует уже принятому в проекте паттерну (`cooldown_jass.py` — тоже
  чистый JASS, тоже фреймы, тоже билд-тайм-генерация массивов из данных
  карты) — минимум новых концепций и рисков.
* Не требует расширять MPQ новыми типами файлов и разбираться с
  FDF-синтаксисом «вслепую» (без клиента для визуальной проверки, ошибки в
  FDF тяжело отлаживать).
* Полностью укладывается в контракт «не трогаем существующие триггеры»: вся
  покупка идёт через штатный `EVENT_PLAYER_UNIT_SELL`, наш код только
  дирижирует, какой юнит-обёртка кому продаётся.
* Внешний вид («красиво как в Dota 2») можно подтянуть постепенно —
  добавлением `BACKDROP` с текстурой рамки, доп. `TEXT`-фреймами для
  golden-цены и т.п., без миграции на FDF; если позже понадобится сложная
  вёрстка — ничто не мешает потом добавить FDF поверх (варианты не
  взаимоисключающие, FDF просто описывает те же фреймы декларативно).

## 4. Пошаговый план (вариант A)

1. **Данные.** Написать в Python (`shop_jass.py`, рядом с `cooldown_jass.py`)
   сборщик каталога: пройтись по `w.shops()`, отфильтровать секретную (`uC74`)
   и боковую (`u010`) лавки (они остаются кликовыми, не входят в общее окно),
   получить у оставшихся ~15 категорий их товары через `w.item_list()`
   (сопоставление unit↔item уже есть), дособрать `goldcost` из
   `ItemData.slk` и путь иконки (переиспользовать `icon_info`), и (при
   наличии полей requires в slk) — список компонентов рецепта по каждому
   товару.
2. **Проверка на дубликаты команд.** Заметили, что часть лавок продублирована
   на Radiant/Dire (`n12B`/`n12N` "Black Market"): каталог должен строиться
   по **названию категории**, а конкретный rawcode юнита-обёртки и
   rawcode лавки-продавца выбираются в рантайме по стороне игрока
   (`GetPlayerId`/`GetOwningPlayer`), то есть таблица в JASS — по три
   колонки на сторону (Sentinel-код / Scourge-код / общий item rawcode), как
   уже неявно закодировано в оригинальном скрипте (`De[]`/`ae[]` тоже общие
   на обе стороны с разными юнитами-обёртками).
3. **JASS-генератор** (`inject`/`remove`, тот же контракт, что у
   `cooldown_jass.inject`): globals-блок (`framehandle array HW_shopBtn`,
   `integer array HW_shopUnitR/HW_shopUnitS/HW_shopItem/HW_shopCost/...`,
   `hashtable HW_shopHT`), functions-блок (создание UI, обработчик клика,
   функция покупки), один вызов в конце `main` (аналог
   `HW_COOLDOWN_CALL`), метки `HW_SHOP_BEGIN/END` для идемпотентности и
   команды `--undo`.
4. **UI-дерево:**
   * кнопка-переключатель у миникарты (`GLUEBUTTON`, своя иконка,
     `FRAMEPOINT_BOTTOMRIGHT` от `ORIGIN_FRAME_MINIMAP`) — открыть/закрыть;
   * панель (`BACKDROP`, `FRAMEPOINT_CENTER` экрана, 0.5×0.6 экрана);
   * вкладки категорий сверху (по одной `GLUEBUTTON` на лавку/категорию,
     текст — имя лавки);
   * сетка иконок (например 8×4) — `GLUEBUTTON` с `BlzFrameSetTexture`,
     подпись цены снизу (`TEXT`-подфрейм), тултип с полным именем и (если
     есть) списком компонентов рецепта — `BlzFrameSetTooltip` на кастомный
     фрейм с несколькими `TEXT`-строками;
   * кнопка «закрыть» (крестик) поверх панели.
   * Все хендлы фреймов кладутся в JASS-массивы по индексам "категория × ячейка",
     плюс обратное сопоставление "id фрейма → индекс товара" в хэш-таблицу
     (`SaveInteger(HW_shopHT, GetHandleId(btn), 0, index)`), как это уже
     делает исходный скрипт карты (`SaveInteger(HY,(KT),74,...)` в `R1`).
5. **Обработчик клика по иконке товара:**
   ```jass
   function HW_ShopBuyClick takes nothing returns nothing
       local player p = GetTriggerPlayer()          -- BlzGetTriggerPlayer()
       local framehandle f = BlzGetTriggerFrame()
       local integer idx = LoadInteger(HW_shopHT, GetHandleId(f), 0)
       call HW_ShopBuy(p, idx)
   endfunction
   ```
   `HW_ShopBuy(p, idx)` вызывает саму покупку одним из двух путей §3/шаг 5
   (order id по позиции `Sellunits` или временный юнит-обёртка +
   `IssueTargetOrder(..,"sell",..)`) — герой/курьер игрока движок находит
   сам (та же логика, что использует `aHv`), нам достаточно направить приказ
   продажи от игрока. Подстраховка: проверить
   `GetPlayerState(p,PLAYER_STATE_RESOURCE_GOLD)` до запуска покупки и молча
   отменить её с текстовым сообщением, если золота не хватает — чтобы не
   плодить лишних временных юнитов.
6. **Порядок разработки:** сначала — минимальная версия с 1 категорией и
   3–4 товарами (проверить, что клик доходит, товар появляется в руках/у
   фонтана, золото снимается один раз, не два); затем — расширение на все
   категории по сгенерированным данным.
7. **Секретная и боковая лавки — не трогаются**, остаются кликовыми зданиями
   как сейчас (задача явно этого просит).

## 6. Риски

* **Order id продажи по индексу `Sellunits`.** Нужно опытно подтвердить,
  что i-я позиция списка соответствует предсказуемому id (`sellunit1+i`),
  иначе придётся идти через явное создание временного юнита-обёртки
  (запасной путь из §4.5) — он универсальнее и не зависит от нумерации.
* **Десинк.** Сам факт создания/показа фреймов безопасен, если делается
  одинаково у всех игроков без ветвления по `GetLocalPlayer()` (в отличие
  от `cooldown_jass`, который *специально* локален, т.к. рисует данные
  чужого выделения). Здесь наоборот: `FRAMEEVENT_CONTROL_CLICK` триггерится
  глобально, и код покупки трогает игровое состояние (золото, юниты,
  предметы) — это обязано идти через обычный триггер (не
  `GetLocalPlayer()`-ветку), иначе разные клиенты создадут разные юниты и
  разойдутся стейтом. Проверить: **не читать/писать состояние от лица
  "локального" игрока** нигде в цепочке покупки, только `p =
  GetTriggerPlayer()`.
* **Гонки при повторных быстрых кликах.** Оригинал уже защищается
  таймером на 1 такт (`R1`) — наш код должен либо переиспользовать этот
  путь (создание предмета через существующую `aHv`, что и происходит
  автоматически при честной "продаже"), либо, если пойдём по пути прямого
  `UnitAddItemById`, добавить свою защиту от двойного клика (временно
  выключать кнопку `BlzFrameSetEnable(f,false)` на 0.3–0.5 с).
  Рекомендация — не создавать свой путь выдачи предмета вообще, только
  дёргать существующий (см. §4.5), тогда все анти-гонки уже есть.
* **Совместимость с уже добавленным `cooldown_jass`-блоком.** Оба блока
  инъецируются перед `function main`; порядок вставки должен быть
  предсказуем (например, всегда после `HW_COOLDOWN_END`, если он есть) —
  `map_fix.py` должен сначала пробовать найти существующий `HW_SHOP_BEGIN`
  для идемпотентности, как это уже делает `cooldown_jass.inject`
  (`remove()` в начале).
* **pjass не проверяет семантику**, только синтаксис — обязательно тестовое
  прохождение в реальном 1.31 клиенте (macOS) перед принятием фикса.
* **FDF (если позже перейдут к варианту B) не валидируется автоматически** —
  ещё один аргумент за вариант A на первом этапе.

## 7. План тестирования

1. `pjass` на собранный `war3map.j` (как уже делается для `cooldown-numbers`)
   — синтаксис/типы.
2. Юнит-тест на 1 категории/3 товарах в тестовой сессии (одиночная игра):
   * открыть/закрыть окно кнопкой;
   * купить товар, стоя рядом с лавкой с героем — товар в инвентаре, золото
     списано один раз;
   * купить, находясь героем **не** у лавки/на другом конце карты — товар
     должен появиться у фонтана/в инвентаре курьера (как при обычной покупке
     "издалека" в этой карте) — сверить с поведением текущей кликовой лавки
     в тех же условиях (базовая линия для сравнения);
   * купить при нехватке золота — покупка должна быть отклонена без побочных
     эффектов (не создан лишний юнит/предмет);
   * быстрый двойной клик — не должно списываться золото дважды/не должно
     появляться два предмета.
3. Мультиплеер (LAN/Battle.net) 2 игрока разных команд — оба видят
   одинаковый каталог с ценами; оба открывают панель одновременно, кликают
   почти одновременно по разным (и по одному и тому же — с расчётом, что
   должно достаться только тому, у кого хватило золота) товару — нет
   десинка, оба видят одинаковый результат.
4. Расширение до всех категорий/лавок, повтор пп. 2 выборочно (3–4
   произвольные категории) плюс тест рецептового товара (визуально —
   тултип с составом; функционально рецепт по-прежнему собирается вручную
   drag&drop, наш магазин лишь продаёт компоненты и сам рецепт-предмет как
   обычный товар).
5. Финальная регрессия: старые кликовые лавки (секретная, боковая, все
   15 категорийных как раньше) продолжают нормально продавать напрямую —
   наш код ничего в их `Sellunits`/абилках не меняет.
